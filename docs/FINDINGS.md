## 2. OBS 무인 설정

**`--headless` 옵션은 없습니다.** OBS 32의 전체 CLI 옵션을 확인했고 헤드리스 모드는 존재하지
않습니다. Qt GUI 앱이라 대화형 데스크톱 세션이 필요하고, 게임 캡처는 그래픽 훅 때문에 더욱
그렇습니다 — Windows 서비스로는 못 돌립니다.

**다만 설정은 100% 무인 자동화가 됩니다.** 배포 시 사용자 온보딩을 스크립트로 만들 수 있다는
뜻이라 UX상 유리합니다.

막는 지점은 **첫 실행 '구성 마법사' 모달 하나뿐**입니다. 이게 떠 있는 동안은 설정 파일 자체가
디스크에 안 써집니다. 한 번 넘기고 나면 `user.ini`에 `[General] FirstRun=true`가 기록되어
다시는 뜨지 않습니다.

### 설정 파일 위치
```
%APPDATA%\obs-studio\user.ini                                  # FirstRun, 프로파일 선택
%APPDATA%\obs-studio\basic\profiles\<이름>\basic.ini
%APPDATA%\obs-studio\basic\scenes\<이름>.json                   # 씬/소스
%APPDATA%\obs-studio\plugin_config\obs-websocket\config.json   # 웹소켓
```

### 웹소켓 활성화 — CLI 인자로는 안 됩니다
`--websocket_port` / `--websocket_password` / `--websocket_ipv4_only` / `--websocket_debug`는
**값만 덮어쓸 뿐 서버를 켜지 않습니다.** (`--websocket_password`는 `auth_required`만 true로
강제.) 활성화 여부는 오직 `config.json`의 `server_enabled`에 있습니다.

```json
{
  "server_enabled": true,     // <- 이것만이 서버를 켭니다
  "server_port": 4455,
  "server_password": "...",   // 첫 실행 시 자동 생성됨
  "auth_required": true,
  "first_load": false
}
```

### 소스 추가는 웹소켓 API로
씬 JSON을 손으로 만들 필요 없이 `CreateInput`으로 추가하는 게 정확합니다. 게임 캡처 설정:

```python
cl.create_input(scene, "League of Legends", "game_capture", {
    "capture_mode": "window",
    "window": "League of Legends (TM) Client:RiotWindowClass:League of Legends.exe",
    "priority": 2,            # 실행 파일로 매칭 (창모드/테두리없는전체화면 모두 대응)
    "capture_cursor": True,
    "anti_cheat_hook": True,
}, True)
```

**`window` 는 OBS 가 나열하는 `제목:클래스:실행파일` 삼중값 그대로 써야 합니다 (2026-09-10 실측).**
실행 파일만 적은 `::League of Legends.exe` 는 OBS 32.2.1 이 자기 창 목록
(`GetInputPropertiesListPropertyItems`, `propertyName=window`) 에서 `itemEnabled=false` 로 표시하고,
게임이 떠 있어도 훅을 시도조차 하지 않습니다 (로그에 `attempting to hook process` 가 없음). 삼중값으로
바꾸자 2초 안에 `shared texture capture successful`. 제목·클래스는 클라이언트 언어와 무관하게 같고,
priority 2 라 매칭 자체는 실행 파일로 됩니다. 앱은 시작 시와 검은 프레임이 이어질 때 이 목록을 읽어
소스를 교정합니다 (`ObsCapture.RepairGameCaptureAsync`).

### 배포 문서에 반드시 넣을 것
- **안전 모드가 WebSocket을 끕니다.** OBS가 비정상 종료되면 다음 실행에 "안전 모드로
  실행하시겠습니까? (서드파티 플러그인, 스크립트 및 **WebSocket** 비활성화됨)"이 뜹니다.
  사용자가 무심코 고르면 위젯이 조용히 죽습니다.
- 웹소켓 서버는 `0.0.0.0`에 바인딩되어 LAN에서 접근 가능합니다. 비밀번호 설정 강조 필요.
- OBS는 씬 컬렉션을 정상 종료 시점뿐 아니라 **변경 시점에도** 디스크에 씁니다 (강제 종료해도
  소스가 살아남는 것을 확인).

## 3. GetSourceScreenshot 성능 — 설계에 직결

각 5회 중앙값, 1920×1080 게임 캡처 소스 기준:

| 포맷 | 해상도 | 중앙값 | 페이로드 |
|---|---|---|---|
| PNG | 1920×1080 | **2755 ms** | 3664 KB |
| PNG | 960×540 | 844 ms | 1161 KB |
| PNG | 640×360 | 394 ms | 596 KB |
| JPG q80 | 1920×1080 | 215 ms | 368 KB |
| **JPG q80** | **960×540** | **69 ms** | 123 KB |
| JPG q80 | 640×360 | 36 ms | 70 KB |

**PNG 풀해상도는 초당 0.36프레임입니다.** 이걸 모르고 `sleep(0.35)`로 루프를 짰다가 실제
간격이 3초가 됐고, 그 결과 증강 선택창 하나를 통째로 놓쳤습니다.

**권장 구조**
- **판정 루프**: JPG q80 @ 960×540 (69 ms, ~14 fps)
- **OCR 프레임**: 호버/선택이 확정된 순간에만 풀해상도 1장

### 검은 프레임 리스크 — 훅된 소스에서만 해당 없음 (조용히 실패하는 경로)
분류를 따로 둡니다: "실패한 접근" 이 아니라 **오류 대신 빈 값이 와서 성공처럼 보이는 API 경로**입니다.
같은 유형을 찾을 때 이 항목을 기준으로 삼으세요.
게임 캡처 소스에서 `GetSourceScreenshot`은 **첫 호출부터 정상 프레임**을 반환했습니다
(`videoActive=True`, 평균 밝기 43.1, 비검정 픽셀 99.7%). 재시도 불필요.

게임이 실행 중이 아닐 때 **크기를 지정하지 않으면** 소스 크기가 0×0 이라 에러로 떨어집니다
(402 `imageWidth is below the minimum of 8`, OBS 32 에서는 D3D11 staging surface 실패 로그).
그러나 **`imageWidth`/`imageHeight` 를 지정하면 에러가 아니라 그 크기의 완전한 검은 프레임이
옵니다** (2026-09-10, OBS 32.2.1). 판정 루프는 항상 960×540 을 지정하므로 "훅 안 됨" 이 "게임은
켜졌는데 선택창이 안 뜸" 과 구별되지 않았고, 앱은 감지 중이라고 표시한 채 두 판을 놓쳤습니다.
지금은 검은 프레임(전 샘플 ≤ 8) 3장 연속을 "소스가 게임을 안 잡음" 으로 보고 상태줄에 띄우며
소스 교정을 한 번 시도합니다 (`Detect.IsBlank`, `RunState.CaptureBlank`).

### 요청 크기가 소스 비율과 다르면 늘려서 줍니다
`imageWidth`/`imageHeight` 를 둘 다 주면 OBS 는 레터박스 없이 **비율을 무시하고 늘립니다**
(1920×1080 소스를 2560×1600, 3440×1440 으로 받아 확인). 그래서 감지 프레임은 소스의 모양을 유지한
채 높이 540 으로 요청합니다 (`Config.DetSizeFor`; 16:9 면 정확히 960×540). 소스 크기는 그림을 받지
않고 `GetSceneItemTransform` 의 `sourceWidth/Height` 로 5초마다 읽습니다 (`ObsCapture.SourceSizeAsync`).

### 클라이언트는 증강 화면을 높이 기준으로 그리고 가로 중앙에 놓습니다 (2026-09-10 실측)
같은 증강 창을 이 모니터가 제공하는 전체화면 15개 해상도(1680×1050, 1600×1024, 1600×900, 1440×1080,
1440×900, 1400×1050, 1366×768, 1360×768, 1280×1024, 1280×960, 1280×800, 1280×768, 1280×720, 1152×864,
1024×768)로 바꿔 가며 OBS 로 녹화했습니다. 카드 세 장의 폭은 어느 해상도에서든 높이의 0.98, 중심은
화면 가로 중심. 즉 좌표 변환은 `s = H/1080`, `x = xb·s + round(W/2 − 960·s)`, `y = yb·s` 하나면 됩니다
(`Detect.Geometry`). 16:9 에서는 오프셋이 0 이라 기존 결과와 비트 단위로 같습니다.

모양을 유지한 프레임으로 15장 전부: 리롤 게이트 3개 모두 0.73 이상(열림 기준 0.45), 숨김 버튼 0.56~0.80,
등급 프리즘 3/3, 카드 제목 OCR 3/3 일치. 반대로 16:9 로 늘린 프레임은 16:9 외 전부에서 게이트가
0.0~0.3 으로 무너졌습니다. 대표 5장은 `tests/fixtures/aspect/` 에 있고 SelfTest `AspectParity` 가 돌립니다.
남은 것: 21:9·32:9 는 이 모니터에 없어 미실측(같은 규칙일 것으로 예상), HUD 스케일 슬라이더.

부수 관찰: 1680×1050 캡처처럼 툴팁이 카드 위로 뒤집혀 올라간 경우, 툴팁 왼쪽 변이 카드 프레임 선과
같은 열에 놓이면 위쪽 탐색이 카드 프레임을 타고 올라가 상단을 90px 높게 잡습니다. 제목 박스가 빗나가
툴팁 OCR 은 실패하지만 플레어·카드 제목 경로는 영향이 없습니다. 툴팁 파인더의 다음 개선 지점.

## 5. 선택창 감지 — 실패한 방식과 작동하는 방식

### ❌ 밝기 임계값 (폐기)
카드/리롤버튼/툴팁 영역의 평균 밝기로 판정 → **다음 게임에서 완전히 무너졌습니다.**

맵이 바뀌자(파란 얼음맵 → 보라색맵) 일반 게임 화면이 "창 열림" 구간에 그대로 들어왔고,
전투 이펙트가 카드 격차 42를 만들어 호버로 오판됐습니다. 한 게임 데이터로 임계값을 뽑고
음성 샘플 검증 없이 배포한 것이 원인입니다.

**교훈: 조명/맵이 바뀌는 환경에서 절대 밝기 임계값을 쓰지 말 것. 그리고 배포 전에 반드시
다양한 조건의 음성 샘플로 검증할 것.**

### ✅ 리롤 버튼 템플릿 매칭
리롤 버튼은 **UI 글리프라 등급·맵·조명과 무관하게 픽셀이 동일**합니다. 그리고
`cv2.TM_CCOEFF_NORMED`는 밝기·대비 선형 변화에 불변 — 위 실패 모드가 정확히 그것입니다.

```
버튼 x 중심: 601, 968, 1337 / y 밴드: 738–790 (1920×1080)
템플릿: gamecap.png 의 (572,740)-(632,786), 60×46
```

**3개 버튼 모두 요구할 것.** 한 게임 프레임에서 왼쪽 버튼만 0.894로 단독 매칭된 사례가
있습니다 (나머지 0.559 / 0.263). 하나만 봤으면 오탐이었습니다.

#### ⚠️ 정정: 단일 템플릿은 충분하지 않았습니다
초기에 "정상 상태" 버튼 하나만 템플릿으로 쓰고 양성 13장 / 음성 16장으로 검증해
**간격 +0.337**을 얻었다고 기록했습니다. **이 수치는 양성 표본이 좁아서 나온 착시였습니다.**

양성을 15장으로 넓혀(호버 전환 프레임 다수 포함) 재평가하니:

| 템플릿 | 양성 최악 | 음성 최악 | 간격 |
|---|---|---|---|
| 정상 상태만 | **0.226** | 0.263 | **-0.036** (역전) |
| 정상 + 상태 2종 | **0.659** | 0.352 | **+0.308** |

정상 상태만 쓰면 **양성 최악값이 음성 최악값보다 낮습니다.** 즉 분리가 안 됩니다.
원인은 버튼의 3상태(정상 / 회색 비활성 / 커서 하이라이트)이고, 실제로 육안 확인된
선택창 프레임 하나가 단일 템플릿에서 0.23을 받았습니다.

**해법은 상태별 템플릿을 만들어 버튼마다 best-match를 쓰는 것입니다.** 상태 2종을
추가하니 간격이 +0.308로 회복됩니다. 히스테리시스는 여전히 필요하지만, 이제는
보조 장치이지 유일한 방어선이 아닙니다.

교훈은 5절 첫머리와 같습니다 — **표본이 좁으면 분리도 수치가 거짓말을 합니다.**

### ⚠️ 리롤 버튼은 상태가 3개
**정상 / 회색 비활성 / 커서 하이라이트.** 템플릿은 정상 상태만 매칭하므로 실제로 열린 창에서
`[0.69, 0.63, 0.95]` 같은 값이 나옵니다. 그래서 **히스테리시스가 필수**입니다:

- **열 때**: 3개 모두 ≥ 0.46, 2프레임 연속 (엄격)
- **유지**: 느슨한 조건 — 다만 아래 미해결 항목 참조
- **닫힘**: 유지 조건이 N프레임 연속 실패

히스테리시스 없이는 창이 0.9초 만에 닫힌 걸로 오판되고, 닫힘 상태에서는 로깅/판정을 안 하므로
**사각지대**가 생깁니다. 실제로 그래서 레벨 3 선택을 놓쳤습니다.

## 6. 호버 및 선택 판정

카드 ROI (1920×1080):
```
L (440,190,760,720)   M (810,190,1130,720)   R (1180,190,1500,720)
툴팁 중앙 프로브 (900,786,1020,860)
```

### 호버 = 카드 밝기 격차 (창 확정 후에만 유효)
창 열림이 템플릿으로 확정된 프레임에서만 측정:

| | 논호버 (n=9) | 호버 (n=3) |
|---|---|---|
| 세 카드 밝기 격차 | 최대 **3.7** | 최소 **16.4** |

임계값 10. argmax가 호버 카드를 정확히 지목합니다.

### ⚠️ 툴팁은 판정 조건에서 빼야 합니다
툴팁을 AND 조건으로 넣었더니 명백한 호버를 대거 놓쳤습니다 — 격차 46, 51, 101인 프레임이
전부 툴팁 미달로 기각. **카드 발광은 즉시, 툴팁은 0.3~0.5초 후**에 뜨기 때문에 두 신호의
교집합만 잡힙니다.

→ 호버 추적은 **카드 격차 단독**, 툴팁은 **OCR 트리거로만** (툴팁이 뜬 프레임에서만 이름 판독).

### 툴팁 크기는 가변, 상단 중앙 앵커는 고정

### ★ 선택 확정 애니메이션이 존재합니다
**"선택됨 상태 애셋이 없다"는 전제는 정적 애셋 기준으로는 맞지만, 선택 순간의 시각적
시그니처는 명확히 존재합니다.** 카드를 클릭하면 선택된 카드가 흰빛으로 터지고 나머지 두 장이
즉시 페이드아웃됩니다.

| 상황 | 선택/호버 카드 | 나머지 두 장 | 나머지/기준선 |

그 방식은 사용자가 빠르게 클릭하면 호버 프레임을 못 잡는 취약점이 있습니다 (레벨 3에서 실제로

|---|---|---|---|---|
| +0.025 | M | 4.30 | 2.25 | 상승 미달 |
| +0.048 | M | 3.40 | 2.92 | 상승 미달 |
| **+0.068** | **M** | **3.47** | **4.11** | **둘 다 통과 — 첫 프레임** |
| +0.137 | M | 3.22 | 5.51 | 계속 상승 |

상승 검사는 카드가 방금 떠난 기준선을 분모로 쓰기 때문에 약 70ms 가 필요합니다. 0.05 로는
18밀리초 차이로 잘렸습니다. 0.15 는 그걸 덮으면서, 맵이 답했던 +0.36초에는 한참 못 미칩니다
(맵 프레임도 cards-down 이라 이 규칙으로는 안 걸립니다 — 그건 이 숫자가 막습니다).

**기각 후보를 항상 남깁니다.** 예전엔 답을 찾는 즉시 멈춰서, 뒤집힘과 선택이 둘 다 빛난 창은
이긴 쪽만 기록됐습니다. 정작 봐야 할 건 진 쪽입니다. 이제 채택 1건과 기각 1건을 같이 남깁니다.
**기각된 슬롯이 채택된 슬롯과 같으면** 하나의 섬광이 앵커를 걸치며 앞뒤로 잡힌 것이고,
**다르면 두 개의 사건**입니다 — 이 구분 자체가 판독에 씁니다.

검증: `--inspect-flare` 로 두 녹화를 새 코드에 다시 통과시킨 결과, 21:14 는 R 그대로,
21:25 는 **L → M 으로 뒤집혔습니다.** 회귀는 SelfTest `FlareTiming` 에 "앵커에서 끝나는
뒤집힘 + 직후의 진짜 선택" 케이스를 추가했습니다.

## 7-2. 판정 기록기 (inspector)

7-1 의 세 건이 공통으로 부딪힌 벽은 **판정이 일어난 프레임이 남아 있지 않다**는 것이었습니다.
덤프는 픽당 두 장(`_read`, `_close`)이고 둘 다 그 프레임이 아닙니다. `_close` 는 숨김 버튼이
창을 최대 1.5초 더 "살아 있음" 으로 붙잡기 때문에 대개 맵 사진입니다.

그래서 창이 열린 순간부터 닫힐 때까지 **모든 프레임과 그 프레임의 계측값**을 남기고,
`http://127.0.0.1:8777/inspect` 에서 되돌려 봅니다. 설정 › 고급의 스위치이고 기본은 꺼짐,
창 하나가 15~25MB, 최근 8개 보관입니다.

### 붙인 자리

새 파이프라인을 만들지 않았습니다. 루프에는 이미 `Observe`(프레임마다 `TraceSample`) 가 있고
SelfTest `--trace` 가 거기에 붙습니다. 기록기는 **같은 자리에 붙는 두 번째 싱크**입니다.
`TraceSample` 에 세 가지만 더했습니다 — `Baseline`(상승 검사의 분모), `HoverSpread`,
`TipPanel`(툴팁 패널 박스). 트레이스는 이미 그것들을 쓴 뒤의 판정문을 쓰기 때문에 필요가
없었고, 기록기는 검사를 **프레임마다 다시** 돌리므로 없으면 못 합니다.

### 프레임은 다시 인코딩하지 않습니다

`Frame.Encoded` 에 OBS 가 보낸 JPEG 바이트를 그대로 실어 둡니다. 재인코딩하면 숫자를 잰
그림과 화면에 뜨는 그림이 달라지는데, 사후분석에서 그건 감당할 수 없는 차이입니다. 덕분에
비용도 전송량 그대로입니다.

### 페이지가 계산합니다

기록에는 원측정값(게이트 3, hide, mean/inner/bright ×3, baseline, spread, 툴팁 박스)만 들어가고,
**섬광 비율과 상승은 페이지가 다시 계산합니다.** `boxes`(17개)와 `limits`(16개)도 같이 실려
페이지가 좌표나 임계값을 하드코딩하지 않습니다. 그래서 임계값을 바꿔 보는 일이 게임을 다시
기다리지 않고 됩니다.

시간축 사건 — 리롤, 채택된 섬광, 기각된 섬광, 앵커, 종료 — 은 프레임 값에서 유도되지 않으므로
루프가 `Observe.Mark` 로 직접 말합니다. 리롤은 두 OCR 스캔 사이의 제목 변화라 시각이 필요해
`Kept.Rerolls` 에 `DateTime At` 을 더했습니다.

### 게임 없이 확인하는 법

    dotnet run --project src/AramOverlay.SelfTest -- --inspect-demo [--serve]
    dotnet run --project src/AramOverlay.SelfTest -- --inspect-flare <state/inspect>

앞의 것은 픽스처 프레임으로 진짜 기록기를 돌려 진짜 서버로 내보내고 라우트를 두드립니다.
프레임 곡선은 서로 무관한 창이라 의미가 없고, 확인하는 것은 계약입니다 — 기록이 써지고,
서빙되고, 페이지가 그릴 `frames`/`boxes`/`limits`/`events`/`verdict` 가 들어 있는지.

뒤의 것이 더 자주 쓰입니다. 녹화에는 프레임마다의 모든 측정값이 들어 있으므로 탐색이 읽는
이력을 **그대로 재구성해 판정을 다시 낼 수 있습니다.** 임계값을 바꿨을 때 답을 아는 실제 창들에
대고 확인하는 유일한 방법입니다 — 로그는 옛 임계값이 내린 결론만 적혀 있어 아무것도 못 합니다.

### 툴팁 패널 박스는 그 프레임의 것이 아닙니다

패널은 OCR 용 전체해상도 그랩에서 찾습니다. 그 그랩은 초당 세 번, 감지 루프와 별도로 돕니다.
그래서 패널 박스는 **옆에 있는 감지 프레임의 값이 절대 아닙니다.** 처음엔 실선으로 나이 없이
그렸다가, 툴팁이 이미 사라진 프레임에 툴팁 박스가 떠 있는 그림이 나왔습니다. 지금은 측정 시각을
같이 기록해(`tipboxage`) 점선 + 나이 표시로 그리고, 스캔 주기(0.35초)보다 오래되면 안 그립니다.

## 11. 게임플레이 영상 분석 (실버 등급 확보)

라이브 플레이를 반복하는 대신 유튜브 게임플레이 영상을 분석했습니다. 다섯 판을 돌려도 못
나왔던 실버 등급을 확보하는 것이 목적이었습니다.

### 영상 프레임은 레포에 커밋하지 말 것
제3자 저작물입니다. 좌표·임계값 같은 **측정 수치는 사실 데이터라 문제없지만**, 프레임 이미지
자체는 공개 레포에 넣으면 안 됩니다. 레포에 넣을 스크린샷은 직접 플레이한 캡처를 쓰세요.
(그래서 영상과 추출 프레임은 전부 임시 폴더에만 두었습니다.)

### 템플릿은 유튜브 재인코딩을 견딥니다 ★
무편집 게임 영상 1편(591프레임) 스코어링 결과:

| 지표 | 값 |
|---|---|
| 게임플레이 노이즈 p50 | 0.239 |
| 노이즈 p90 | 0.320 |
| 실제 선택창 | 0.586 ~ 0.954 |

**네이티브에서 정한 임계값 0.46이 압축 영상에서도 그대로 작동합니다.** 영상용으로 임계값을
따로 잡을 필요가 없습니다. 이는 템플릿 매칭이 밝기 휴리스틱보다 견고하다는 또 하나의 증거입니다.

### 영상 수율과 함정
- 15분 영상 1편당 선택창 **3~8개**. 실제 게임 한 판(4~5회)과 비슷하거나 조금 나은 수준
- **영상 길이로 무편집 여부를 알 수 없습니다.** 15분짜리 최신 영상이 선택창 0개였습니다
  (편집으로 잘려나감). 6편 중 1편은 0개, 1편은 8개로 편차가 큽니다
- 영상의 이점은 편당 수율이 아니라 **사용자 플레이 없이 배치로 돌릴 수 있다는 것**입니다
- 최신 영상일수록 짧은 편집본 경향이 있습니다. 다만 **최신성이 중요한 건 증강 "목록"이지
  UI 크롬이 아닙니다.** 리롤 버튼·카드 좌표·툴팁 위치는 패치로 잘 안 바뀌므로 구조 검증에는
  오래된 무편집 영상도 유효합니다

### 등급 판별 — 채도가 아니라 명도
카드 상단 테두리 스트립 `(470,188)-(730,206)` 등 3개 카드의 HSV 중앙값:

| 등급 | hue | sat | **val** | 카드 ROI 기준선 |
|---|---|---|---|---|
| **실버** | 81.7 | 35.4 | **134.9** | **37.5** |
| 골드 | 15~33 | 24~48 | 178~209 | ~53 |
| 프리즘 | 115~132 | 19~31 | 186~210 | ~70 |

- **골드/프리즘은 hue로 갈립니다** (28~30 vs 116~119, 네이티브 기준)
- **실버는 val로 갈립니다** (135 vs 178+). 회색 테두리라 어둡습니다
- **채도(sat)는 쓸 수 없습니다.** 프리즘 프레임이 sat 18.8로 나온 사례가 있어 실버(35.4)보다
  낮았습니다. 처음에 sat < 22를 실버 기준으로 세웠다가 오탐했습니다

### 분류 시 반드시 안정 프레임을 고를 것 ★
구간 내 **템플릿 점수가 가장 높은 프레임**으로 분류하면 안 됩니다. 카드 등장 애니메이션
중에도 리롤 버튼은 이미 정상 렌더링되어 점수가 높지만, 카드 자체는 흰빛으로 탈색되어 있어
등급 판별이 완전히 틀립니다. 실제로 이 실수로 애니메이션 프레임을 "실버"로 오탐했습니다.

**안정 프레임은 카드 내부가 어두운 프레임입니다** (내부 밝기 ~18~36). 애니메이션 중에는
90 이상으로 밝습니다. 구간 내에서 카드 내부가 가장 어두운 프레임을 고르세요.

### 실버 등급 검증 결과 ★
실버 선택창 1건(7프레임)의 프레임별 측정:

| 프레임 | 템플릿 L/M/R | 카드 L/M/R | 기준선 | 격차 |
|---|---|---|---|---|
| f0347 | 0.98 / 0.95 / 0.98 | 66.8 / 67.9 / 61.1 | 66.8 | 6.8 (등장 애니메이션) |
| f0348 | 0.99 / 0.57 / 0.99 | 40.4 / 37.5 / 34.3 | 37.5 | 6.1 |
| f0349 | 0.57 / 0.98 / 0.76 | 40.4 / 38.9 / **59.9** | 40.4 | **21.1** (R 호버) |
| f0350 | 0.58 / 0.98 / 0.75 | 40.3 / 37.3 / 35.6 | 37.3 | 4.7 |
| f0351 | 0.78 / 0.99 / 0.75 | **58.5** / 37.5 / 35.4 | 37.5 | **23.0** (L 호버) |
| f0352 | 0.75 / 0.45 / 0.75 | 42.7 / 37.5 / 35.4 | 37.5 | 7.3 |

**결론:**
1. **템플릿 게이트가 실버에서 작동합니다.** 개별 버튼이 3상태 때문에 떨어지는 패턴도
   골드/프리즘과 동일합니다 (히스테리시스 필요성 재확인)
2. **호버 임계값 10이 실버에서도 유효합니다.** 논호버 4.7~7.3 / 호버 21.1~23.0
3. 등급 사다리 완성: 카드 기준선 실버 37.5 / 골드 53 / 프리즘 70

### 도구 선택 교훈
프레임 추출은 **반드시 ffmpeg로** 하세요. OpenCV의 `VideoCapture`를 파이썬 루프에서 돌리면
순차 디코딩이든 `CAP_PROP_POS_FRAMES` 탐색이든 15분 1080p60 파일 하나에 CPU 40분 이상
걸립니다 (탐색은 키프레임 간격이 길어 더 나빴습니다). ffmpeg `-vf fps=1/1.5`는 같은 파일을
**27초에 처리**합니다 (32배속). 파이썬은 추출된 JPEG를 읽기만 하면 됩니다.

### 남은 한계
- **실버 샘플이 1건뿐입니다.** val < 160 기준은 이 1건에서 나온 잠정치입니다
- 등급별 hue/val은 맵 배경이 테두리 스트립에 섞여 들어가면 흔들립니다. 스트립 위치를
  프레임마다 카드 경계에서 찾아내면 더 정확해집니다 (현재는 고정 좌표)

| 85 | 36.1 / 18.9 | 37.5 / 19.8 | 102.1 / 86.0 | 4.35 |

| 87~88 | 38.9 / 25.3 | 41.9 / 27.1 | 116.4 / 116.1 | 4.28 |
| 89 (상점 열림) | 23.2 / 31.9 | 23.2 / 20.3 | 55.4 / 44.2 | 1.39 |

이 프레임들에서 **리롤 버튼 게이트는 이미 죽어 있습니다** (0.83/0.81/0.80 → -0.12/0.12/0.10).
플레어 표본을 `CardsUp`으로 거르면 안 되는 이유입니다.

### 판정 조건 — 두 축, 둘 다 필요

| | inner 비율 (카드 간) | 자기 기준선 대비 (시간축) |
|---|---|---|
| 선택 플레어 | 4.28 ~ 6.64 | 3.8 ~ 8.5 |
| 상점 패널 | 1.39 ~ 1.58 | 2.3 ~ 2.6 |
| 호버 (창 열림) | 1.0 ~ 2.6 | 약 1 |
| 창 종료 후 맵 | 1.0 ~ 1.8 | 제각각 |

상점이 시간축 조건을 통과합니다 — 패널 경계가 카드 박스를 가로지르면 한 장만 밝아진 채
유지되기 때문입니다. 카드 간 비율만이 그걸 "정적인 것"으로 잡아냅니다. 반대로 시간축은
호버와 맵을 걸러냅니다. **하나로는 부족합니다.**

내부 박스(`CardInteriors`)를 쓰는 이유: 작고 중앙에 있어 가림막 경계에 걸치지 않습니다.
같은 상점 프레임에서 카드 전체 평균은 노출된 카드를 **5.4배**로 만들어, 셋 중 둘이 패널에
덮인 채로도 확신에 찬 오답을 냅니다.

### 폐기한 조건 — 밝은 픽셀 비율

두 번째 축 후보로 "200 이상 픽셀 비율"을 먼저 시도했고, ffmpeg으로 재니 완벽히 분리됐습니다
(평상시 0%, 플레어 3~12%). **ffmpeg의 gray 변환이 limited range라 생긴 착시였습니다.**
앱의 full-range 연산으로 다시 재면 무너집니다:

| 측정 | 평상시 최대 | 플레어 |
|---|---|---|
| 카드 박스 200+ | 16.9% | 8.7% |
| 내부 박스 200+ | 12.3% | 1.2% |
| 카드 박스 245+ | 5.0% | **0.0%** |

플레어의 흰빛은 챔피언 모양 버스트라 내부 박스를 채우지 않고, 애초에 순백이 아닙니다.
**측정값은 그것을 잰 연산만큼만 유효합니다.** 이걸 잡아낸 건 프로토타이핑 도구가 아니라
`SelfTest --flare`로 앱 자신의 코드에 통과시켜 본 것이었습니다.

### 실패한 조건 — 승자 상승 + 패자 하강

"승자가 밝아지는 동안 패자는 어두워진다"는 플레어 **첫 2프레임만** 성립하고 그 뒤 뒤집힙니다.
패자 카드가 녹아 없어지면서 뒤의 맵이 드러나는데, 맵이 카드 내부보다 밝기 때문입니다
(패자 inner 15 → 26, 승자 20 → 117). 5프레임으로 조정한 조건은 진짜 플레어를 기각하고,
기각된 플레어는 이미 오답을 낸 폴백으로 떨어집니다.

### 검증

- `SelfTest --flare`: 실제 게임 덤프 64프레임 → inner 비율 최대 **2.59**, 통과 0건
- `SelfTest --flare`: 영상 169프레임 → 통과 **5건**, 전부 플레어 구간(84~88)
- `SelfTest --replay`: 같은 영상을 창 하나로 재생 → **R을 플레어로 선택** (4.28배 / 8.51배)

### 기준점은 종료가 아니라 "카드가 마지막으로 보인 프레임"

종료 판정은 숨김 버튼을 기다리는데, 그 간격이 유계가 아닙니다. 이 영상에서 숨김 버튼은
카드가 사라진 뒤에도 **1.5초 넘게 1.00으로 매칭**됐습니다 (상점을 여는 동안 하단 덱 버튼이
계속 보임). 종료 시점을 기준으로 잡으면 그 간격이 플레어를 탐색 범위 밖으로 밀어냅니다.

## 13. 툴팁 패널은 고정 박스가 아닙니다

`HoverTooltip = Box(620, 788, 1330, 842)` 은 "글자가 걸릴 만한 자리"에 놓은 띠였습니다.
실제 패널은 내용에 따라 위치와 크기가 변합니다.

손으로 표시한 뒤 `Cv.Edges` 와 같은 3×3 Sobel 로 각 변을 재정렬한 값입니다.

| 프레임 | 폭 | 패널 y | 높이 | 중심 x | 제목 높이 |
|---|---|---|---|---|---|
| video_f55 (Deft) | 222 | 784~905 | 121 | 963.5 | 78 |
| lv15_03_hovM | 313 | 783~911 | 128 | 962.5 | 80 |
| aug_lv7_11 (한글) | 637 | 785~1042 | 257 | 962.5 | 79 |
| frame_05 | 683 | 785~997 | 212 | 962.0 | 78 |
| **Dropkick (뒤집힘)** | **697** | **440~781** | **341** | **963.5** | — |

### 고정된 것

- **앵커 y = 783.** 다섯 장 모두. 정상일 땐 패널 **상단**, 뒤집히면 패널 **하단**이 여기 붙습니다
- **가로 중심 962** (960.5~963.5)
- **제목 줄 높이 80**, 아래에 구분선이 **y 862~865** 에 4px. 앵커에서 +79
- **아이콘 폭 62~74**, 패널 좌측
- 테두리는 이중입니다 — 바깥 783, 안쪽 786

### 변하는 것

폭 222~697(가장 긴 텍스트 줄), 본문 높이 42~175(줄 수, 한 줄 35~45px).

### 뒤집힘

`1080 - 783 = 297` 보다 높은 패널은 아래로 자랄 자리가 없어 **위로 뒤집혀 바닥을 앵커에 붙입니다.**
실측: 257 은 아래(바닥 1042), 341 은 뒤집힘(바닥 781). 경계는 그 사이입니다.

실전에서 `Triggered Inferno`(4문단 + 이탤릭 + 스탯 2줄)가 뒤집혀 y 390~780 에 떴습니다.
그때 고정 박스(788~842)는 패널 완전히 아래의 빈 공간이라 **아무것도 읽지 못합니다.**

### 검출 — 앵커선 하나에서 출발합니다

```
1. y=783 ±6 에서 길이 200px 이상, 중심 960±45 인 가로 테두리  -> 툴팁 있음
2. 앵커 아래 80px 구간에서 중앙 960 기준 좌우 세로 테두리      -> 하단 툴팁
3. 없으면 위쪽 80px 구간에서 동일하게                          -> 뒤집힘
4. 제목 = (좌 + 아이콘폭, 상단+4) ~ (우, 상단+80)
5. 실패하면 기존 고정 박스로 폴백
```

**폭은 가로 구간이 아니라 세로 테두리로 잽니다.** 리롤 버튼의 아래 테두리가 `y 743+41 = 784`
로 앵커와 같은 줄이라, 가로로 이으면 버튼+패널+버튼이 하나가 됩니다 — `frame_05` 에서
683 대신 807 이 나오고 판정이 뒤집혔습니다.

### 실패했던 판별식

- **"앵커 위가 아래보다 어두우면 뒤집힘"** — 앵커 위는 정상 상태에서도 흐려진 배경이라
  어둡고 균일합니다(평균 22, 편차 1). 아래 패널은 글자 때문에 오히려 밝고 결이 있습니다
  (평균 50, 편차 64). 반대로 나옵니다
- **가운데 리롤 버튼 게이트 붕괴** — 뒤집힌 패널이 가운데 버튼을 덮는 건 맞지만
  (Dropkick 에서 [0.77, **-0.04**, 0.57]), 버튼 자체의 애니메이션 상태로도 같은 값이
  나옵니다. 트레이스 34창에서 253 프레임이 걸렸고 열어본 것들은 전부 정상이었습니다
- **중앙에서 바깥으로 처음 만난 세로선** — 툴팁 **아이콘 테두리**(높이 55px, 지지율 71%)가
  패널 바깥 테두리보다 안쪽이라 먼저 걸립니다. 좌우가 165 대 235 로 비대칭이 되어 하단
  판정이 실패하고 위쪽에서 엉뚱한 것을 잡았습니다. **가장 넓은 대칭 쌍**을 골라야 합니다
- **리롤 버튼 세로변을 양방향에서 배제** — 위쪽에서만 배제해야 합니다. 아래쪽에서도 빼면
  `frame_05` 의 오른쪽 경계 1302 가 버튼 왼쪽 1304 와 2px 차이로 같이 잘려나갑니다

### 같은 패널이 카드 제목도 가립니다

검출은 툴팁을 못 읽는 문제만 풉니다. 뒤집힌 패널은 **카드 제목 위에 놓여** OCR 을 잘라먹습니다.

| 창 | 잘린 읽기 | 점수 | 결과 |
|---|---|---|---|
| 16:58 lv3 | `'Drop'` | 0.67 | DropBear 로 오발행 (정답 Dropkick) |
| 00:20 lv3 | `'Trigger'` | 0.61 | Triggered Inferno, 우연히 정답 |

둘 다 임계값 0.60 을 겨우 넘겼고, 앞서 온전히 읽어둔 1.00 짜리를 덮어썼습니다.
`ScanCardsAsync` 가 슬롯별 **최신** 읽기를 채택하기 때문입니다.

### 가려진 제목은 툴팁에서 읽습니다

툴팁은 같은 이름을 더 큰 글자로, 아무것에도 가려지지 않은 채 보여줍니다. 그러니 카드 제목이
0.90 미만으로 읽힌 슬롯은 툴팁의 이름을 대신 씁니다.

다만 툴팁이 그 슬롯의 것이라는 보장은 없습니다. 클릭하는 순간 커서는 반드시 그 카드 위에
있지만, **우리가 가진 툴팁은 클릭 순간의 것이 아닙니다.** 프로브가 0.35 초 주기라 실제
읽힌 시점은 늘 앞섭니다 — 실측 간격 0.20 / 0.33 / 0.44 / 0.47 / 0.47 초. 17:04 창에서는
그 사이에 커서가 M 에서 R 로 옮겨갔고, 툴팁은 `Hextech Soul`(M) 인데 정답은
`Stackosaurus Rex`(R) 였습니다.

확인은 공짜입니다. **툴팁은 카드 한 장만 가리므로 나머지 둘은 항상 읽힙니다.**

```
툴팁 이름이 나머지 두 슬롯의 확신 있는(>= 0.90) 제목 중 하나와 같다
      -> 커서가 아직 거기 있었던 것이므로 기각, 그 슬롯 자신의 읽기를 유지
그렇지 않다
      -> 다른 데서 왔을 곳이 없으므로 이 슬롯의 것, 채택
```

| 창 | 슬롯 | 툴팁 | 나머지 둘 | 결과 |
|---|---|---|---|---|
| 16:58 | L (`'Drop'` 0.67) | Dropkick | Cruelty / Mad Scientist | 채택 → **Dropkick** |
| 17:04 | R (1.00) | Hextech Soul | **M = Hextech Soul** | 기각 → R 자신의 읽기 |
| 00:20 | L (`'Trigger'` 0.61) | Triggered Inferno | Mystic Punch / — | 채택 |
